# Task: User Stories and Acceptance Criteria

Project: AI-Native University Student-Support Case Agent

## Introduction

For our BSE4104 group project we are building a bounded AI agent that helps students with academic policy questions, timetable checks, and routes anything more complicated to support staff as a ticket. My part of the requirements work was writing the user stories and acceptance criteria below.

A few of the stories mention RAG, which stands for Retrieval-Augmented Generation. In simple terms, instead of letting the AI answer purely from what it was trained on, RAG makes it look up the actual policy or handbook document first and answer based on what it actually found there. That is what keeps the answers grounded and traceable to a real source instead of the AI making something up.

I wrote these stories around the safety boundaries our team already agreed on. The agent can answer questions, check timetables, check case status, and create tickets, but it can never touch grades, admissions, fees, or discipline. Those hard limits show up directly in a couple of the stories below, mainly US-09 and US-10.

Each story follows the standard "As a... I want... so that..." format, with acceptance criteria written underneath as things that can actually be tested.

## User Stories

**US-01 (Must)** As a student, I want to ask questions about academic policies in plain language, so I get accurate answers without digging through the handbook myself.

- When a policy or handbook document exists in the knowledge base and a student asks something related to it, the agent should answer using that document and mention which section it came from.
- If the question falls outside what is covered in an approved document, the agent should say so instead of making something up.
- The agent should never add details to an answer that are not actually written in the source document.

**US-02 (Could)** As a student, I want to know whether an answer came from an official document or not, so I know how much to trust it.

- Answers pulled from a retrieved document should show where that information came from.
- If nothing relevant was found but the agent still tries to help, it should say the answer is not backed by an official source.
- A student asking for more detail on a citation should be able to see the actual section referenced.

**US-03 (Must)** As a student, I want to check my current timetable, so I know where and when my classes are without waiting on staff.

- With a valid student ID, the timetable should come from the timetable service directly, not from the LLM guessing.
- An invalid or unrecognized ID should return a clear "not found" message, not a made up schedule.
- If the timetable changes, the next time the student checks it should show the updated version.

**US-04 (Should)** As a student, I want to check the status of a case I opened earlier, so I know if it has been resolved without asking around.

- With a valid case ID tied to the student, the agent should pull the current status straight from the case database.
- If the student just says "my case" and only has one open, the agent should confirm which case before answering.
- If no matching case exists, the agent should say so rather than guessing a status.

**US-05 (Should)** As a student, I want the agent to remember which case we are talking about during a session, so I do not have to repeat the case ID every time.

- Once a case has been mentioned, follow up questions in the same session should use it automatically.
- If the student brings up a different case ID partway through, the agent should switch to that one.
- Once a session ends and a new one starts, the agent should confirm the active case again instead of assuming it is still the same one.

**US-06 (Must)** As a student, I want to raise a support ticket when my question cannot be handled directly, so a staff member can look into my specific situation.

- If an inquiry falls outside what the RAG lookup or timetable check can answer, the agent should draft a ticket summary and ask the student to confirm before sending it.
- Once confirmed, the ticket should get a unique ID generated by the system, not the LLM.
- The ticket should be routed to the right staff queue by a fixed rule, not left to the LLM to decide on its own.

**US-07 (Should)** As a member of support staff, I want escalated tickets to arrive with a short summary, so I do not have to read through the whole conversation to understand the issue.

- Every escalated ticket should include a short auto generated summary along with the student's original message.
- Tickets should be tagged to the right queue based on category, like timetable, policy, or admin.
- The summary should never leave out or twist any of the facts from what the student actually said.

**US-08 (Should)** As a student, I want the agent to ask me to clarify when my question is unclear, so it does not guess and get it wrong.

- If a question could reasonably mean more than one thing, the agent should ask a clarifying question rather than picking an interpretation at random.
- Once the student clarifies, the agent should route the conversation correctly from there.
- If clarification does not resolve things after two tries, the agent should offer to hand the student off to a real person.

**US-09 (Must)** As a student, I want the agent to say no to anything outside its allowed scope, so I know it cannot make decisions like changing grades or handling admissions or discipline.

- A request to change a grade, approve admission, or take disciplinary action should be declined, with an explanation that it is outside what the agent is allowed to do.
- Where possible, the agent should point the student toward the correct human office or process instead.
- These refusals should be enforced by a hard coded rule that blocks the request before the AI even gets a chance to respond to it.

**US-10 (Must)** As the system, I want to check a student's identity and permissions before showing personal data like timetables or case status, so private information does not end up with the wrong person.

- A request for personal data from someone who is not authenticated should be denied and prompted to log in.
- An authenticated student should not be able to view another student's case or timetable.
- Failed permission checks should be logged so they can be reviewed later.

**US-11 (Should)** As someone on the quality and security side of the project, I want a record of what the agent did and why, so I can check the system actually stayed inside its bounded scope.

- Every tool call the agent makes, whether it is a document lookup, timetable check, or ticket creation, should be logged with what went in and what came out.
- If a request gets declined or escalated because of a safety boundary, the log should show which rule triggered that.
- Each of the 30 test scenarios in our evaluation suite should have a trace that can be pulled up for grading.

**US-12 (Could)** As part of the team, I want each story linked back to our AI Boundary Matrix, so it is easy to see which parts are AI driven and which are hard rules.

To sum that mapping up in plain terms:

- US-01 and US-02 sit on the AI side, retrieval and generation, and stay within "no admissions, grading, or disciplinary content."
- US-03 is fully deterministic. The timetable is a database lookup, never generated by the LLM.
- US-04 and US-05 mix both. The data comes from the database but the AI keeps track of context during the conversation.
- US-06 and US-08 are AI driven, classification and drafting, but ticket creation always needs the student to confirm first.
- US-09 is a deterministic guardrail, the hard limit on grades, admissions, and discipline.
- US-07 is AI, summarizing, but it should never change the facts.
- US-11 is system level logging for full traceability.
- US-10 is deterministic, authentication and permission checks.
